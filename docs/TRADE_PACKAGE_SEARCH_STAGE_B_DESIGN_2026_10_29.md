# Stage B design and implementation record: salary-aware trade construction

Status: **Stage B is now implemented and verified**, following the subsequent explicit implementation request. The text below preserves the original design proposal; measured implementation details, deviations, discovery losses/gains, commands and verification are in the Stage B section of [the performance notes](SIMULATION_SPEED_2026_10_29.md#performance-task-3-stage-b-implemented). Evidence is under `output/salary-search-stage-b/`; its `reference/` preserves the pre-edit Stage A backend.

The implementation reuses existing authoritative first-issue financial/roster helpers rather than changing their public report shape. Raw financial facts and exact movement classes are bounded and review-local. Repair seeds use actual flows and authoritative blocked reasons, with quote scores used only for bounded routing guidance; complete routes receive full authoritative participant approval. This intentionally changes discovery and facilitator seed priority. It does not claim Stage A outcome parity or preservation of every formerly found valid offer.

## Why this is a separate redesign

`buyer_offer_packages_for_value` receives a value, salary, and excluded player IDs, not the complete target asset flow. Its callers include single-player inquiries and multi-asset finder requests. Salary alone cannot stand in for the actual outgoing assets: matching credit can differ from nominal salary, unresolved/expired contracts require special handling, and future-season payroll guardrails depend on each contract. Roster effects also depend on actual player counts.

`trade_salary_legality` delegates to `salary_matching_issue`, which checks practical matching tolerance, guaranteed matching credit, current payroll/hard-cap changes and three future years. The latter returns the first issue string, not all violations or a structured repair classification. `simulate_ai_trades` selects blocked facilitator seeds using actual participant net values and distinct team pairs. Simply skipping evaluation of financially blocked candidates would remove information used to find three-team agreements.

There is no standalone second-apron salary-aggregation prohibition implemented in the inspected authoritative trade rules. The supported model has aggregate package salary/credit and hard-cap guardrails. Search must not invent a separate approximate aggregation rule. Any additional financial rule needs an authoritative rule change and its own tests before search can use it.

## Bounded implementation proposal

1. Add an internal `TradeSearchIntent` containing normalized seller outgoing assets, receiver identities, date, seed, config and review identity. Single-player callers can supply their existing target; multi-asset finders must supply all selected assets. Keep the public value-only generator compatible, using Stage A behavior when intent is unavailable.
2. Add a structured report to the authoritative financial/roster helpers. Keep current public first-issue messages and status unchanged. Report all supported violations, affected team/year, unresolved fields and rule identity. Use the same calculation functions as `trade_salary_legality` and `roster_count_issues`; add no parallel salary formulas.
   Before classifying the full universe, compile review-local raw financial facts with the existing authoritative helpers: each team's current and three future payroll totals (including waived money and unresolved flags), each contract's actual salary and guaranteed matching credit, cap lines, and roster membership. Preserve the existing addition order and boundary arithmetic. These are inputs, not cached approval or legality conclusions. Rebuild on any review-state change, and compile fresh facts for settlement. Otherwise checking every player group could cost more salary scans than the old shortlist evaluation; measure that explicitly.
3. Classify identical player-group movements once per review/intent, before expanding pick variants. Picks do not change salary or roster count, but their ownership, protections, swaps, fallback rights, Stepien and investment checks still run per complete package. Classes are direct-feasible, unresolved/manual, repairable salary/roster, and terminally illegal under supported rules. Hard-cap overages alone are not proof of terminal illegality: a third team may absorb salary.
4. Build the direct shortlist from the unchanged player/pick universe and configured breadth, filling the existing requested capacity with feasible candidates where possible. Keep a separate repair frontier and a complete audit ledger of displaced candidates. Preserve the existing 16 distinct facilitator seed pairs, 64 total evaluated completions, 24 per seed, target/buyer breadth, market slots and action frequency. Do not reduce these budgets to make timing results look better.
5. Repair records contain complete normalized flows, terms and authoritative blocked reasons. Rank them with actual compact participant valuations, retaining the information currently used for facilitator ordering. Do not use rough quote scores to infer premium-return adequacy, willingness to move a core player, or participant consent. Reuse Stage A player/pick components where their full dependencies match; do not reuse proposal-ID/seed-dependent personality decisions across proposals.
6. Reuse `facilitator_candidates` to propose redirections/extra salary and third-party consideration. Each completed route must send and receive valid consideration for every team. Recheck complete authoritative legality, core commitments, premium return, investment limits and every participant's approval. Transaction application always uses fresh current state and existing authoritative application checks.

## Required acceptance gates before enabling Stage B

- Exact arithmetic financial boundary tests: matching floor and tolerance; cap-room/tax-line absorption; partially guaranteed outgoing credit; unresolved/expired contracts; current and each future hard-cap guardrail; aggregate package credits and any independently added aggregation rule; roster minimum/maximum and legal salary-reducing moves from existing overages.
- Discovery tests for pick-only absorption, protections, swaps, collateral/Stepien restrictions and bounded facilitator repair. Retain the existing synthetic all-party-approved facilitator fixture; reject a third party receiving assets without sending consideration or sending without receiving.
- Premium fixtures with 90+, 92+ and 96 players. Accumulating weak depth and rough package value never overrides `premium_return_issue`, core commitments or pick-investment limits.
- Paired checkpoint probes on the ordinary, deadline and July 1 inputs recorded for Stage A, both seeds 17/29. Record ordered package lists, direct/multi-team offers, protected/swapped rights, accepted/rejected decisions, and a proposal-by-proposal lost/gained ledger.
- For every sampled lost previously valid proposal, show full assets, terms and old approval, then explain its displacement/classification. Re-evaluate lost candidates authoritatively against the same snapshot. Separate budget displacement from invalid classification and from intentional search-policy changes; no aggregate-only parity claim.
- Fresh repeated real app-action timing and RSS measurements, performed sequentially. Stage B intentionally changes discovery, so old/new saved-state equality is not its acceptance criterion. Daily/bulk and midpoint export/reload must still agree within Stage B, including offers, transactions and ordered events. UI explanations and animation behavior remain unchanged.

Use a separate Stage-A source reference before implementing B. Stage A results are not evidence that B is safe or faster.
