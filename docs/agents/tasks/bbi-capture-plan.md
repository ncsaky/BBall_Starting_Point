## Capture counts and time estimates

These are planning scenarios, not observed paid performance. Time a 12-player feasibility batch, then one full-league batch on day 1. Use the resulting B, N, P, R, S and seconds/query to update the ledger. There is no defensible fixed total before export scope is known.

- **Best case, wide all-league exports:** 14 season entries × 3 representations = **42 exports**, or **56** including value+, if one export contains the entire metric library. At 2 minutes/export plus metadata and cell/count checks, allow **3–5 hours** for base player data, **8–16 hours total** including definitions, postseason, other tool-only tables, reconciliation and backups. Fourteen years is an example based on the Skills full-version label, not a promise about every tool.
- **Family tables / 25 metrics at a time:** ceil(700/25)=28 batches × 14 seasons × 3 representations = **1,176 queries/exports** (1,568 with value+). At 1–2 minutes/query, base data takes **20–40 hours**, plus **8–20 hours** for unique tool outputs and QA. More than 700 metrics increases the count. Multi-year exports reduce it if season labels/populations stay correct.
- **Manual pages, 600 rows, 100/page:** the same example needs **7,056 page saves** for three representations. At 30–60 seconds/page, **59–118 hours** for base data before metadata and review. An exposed All control reduces this to one large rendered table per query, provided all rows really render.
- **One metric/table:** 700 × 14 × 3 = **29,400 queries** before pagination. That is **490 hours at one minute/query**. Do not quietly promise a complete month-long archive through this route; prioritize the core seasons/families and seek a permitted provider export.
- Per-player profiles, unique shot-map splits, similarity reference tables and role counterfactuals can dominate time if they lack bulk equivalents. For illustration, 600 players × 14 seasons = **8,400 individual views** per unique output. Numeric duplication across tools need not be re-collected. Record base-data coverage separately from derived scenario coverage.

“Everything” means all legitimately exposed base records, representations and unique tool outputs. It cannot mean every possible custom five-player lineup, roster constraint set, four-player WOWY group or arbitrary date range; these combinations are effectively unbounded. Preserve definitions and all exposed underlying tables, plus the useful scenario outputs and their settings. Mark any remaining uniquely exposed fields as gaps, not complete.

The cache uses compressed per-batch normalized JSON so each new export does not rewrite all previous seasons. Millions of cells still warrant checking free disk space before capture. Keep raw files, compressed normalized batches, the index and a second personal backup together; exact storage depends on exported text and representation overlap. A synthetic 10,000-row long-form benchmark imported in **0.257 seconds**, read back in **0.052 seconds**, and produced **105,220 compressed bytes** from **557,872 raw bytes** (index 5,380 bytes before the richer per-field audit was added). These are illustrative local measurements, not paid-export throughput guarantees; `data/research/bbi/benchmark.json` retains the result.

## Offline import instructions

No packages were added. Runtime uses Python's standard library. From the repository root:

```sh
PYTHONPATH=src .venv/bin/python -m nba_gm_data.bbi_import \
  /absolute/path/to/export.csv \
  --metadata /absolute/path/to/export.metadata.json
```

Optional `--universe` selects another canonical identity file; `--cache-dir` selects an isolated archive. Do **not** test synthetic captures in the default real cache. Synthetic fixtures in the test suite use temporary directories; only the historical public demo is in the checked working cache.

Accepted inputs:

- UTF-8 CSV/TSV with unique headers, flat JSON row objects, or JSON `{columns: [...], rows: [[...]]}`. Long form uses `Player`, `Season`, `metric_name`, `raw_value`, `percentile`, `grade`, `sample_size` and optional `sample_unit`, `units`, `percentile_scale`, `missing_reason`, `value_plus`. Identity column aliases are declared in the module. A year-only season needs `year_convention: ending` or `starting`.
- Wide form can use exact metric names in separate captures with metadata `representation: raw_value`, `percentile`, `grade` or `value_plus`; or headers such as `Ball Screen Navigation (Value)`, `(Percentile)`, `(Grade)`, `(N)`. An explicit `column_map` handles other spellings: `{"nav_pct":{"metric":"Ball Screen Navigation","representation":"percentile"}}`. Preserve the original export; do not silently rename its bytes.
- Saved rendered HTML tables with header/data cells, including the real Shiny demo's extra filter row and blank rank header. Multiple tables require a zero-based `table_index`. Script-only data/loading pages are rejected. Table-only saving is preferable; whole application HTML can include hidden or duplicate tables.
- For aggregate/lineup/team tables, retain the raw file and metadata with all identifying/context columns. Rows without an individual identity remain unmatched; they do not become individual evidence. The importer preserves their fields, but does not invent a player allocation of lineup outcomes.

Output is `data/research/bbi/normalized.json` (small batch/coverage index), `normalized/<batch-id>.json.gz` (long-form normalized cells), and `raw/<sha256>.<extension>` (exact source bytes). The metadata lives in the index, and each cell points to batch ID and one-based data-row ordinal. Raw/percentile/grade/sample/season/retrieval remain separate; displayed source text and units are retained. Role labels, provider models and unknown fields stay provider/context evidence, never relabeled technique. Identical bytes plus identical metadata import once; repeated bytes with changed metadata are flagged and preserved. Per-field coverage reports matched cells, raw values, percentiles, grades, sample sizes, known sample units and missing values separately. These are captured-cell counts including overlaps, not claims about the number of unique eligible league players. Within-batch duplicate player/season/team/metric rows are reported. Cross-batch overlaps remain separate; the estimator never sums them.

## What the estimator will use automatically

`InputEstimator.from_local(root)` loads the indexed BBI cache; therefore `scripts/build_player_inputs.py` needs no change. Cache absence performs no write or date/RNG operation and leaves output identical. A missing/corrupt referenced batch or unsupported schema raises a visible error rather than silently disabling evidence.

Only matched **observed regular-season totals from 2023–24, 2024–25 or 2025–26**, in complete batches with **season-wide all-player percentiles**, an explicit percentile scale and confirmed favorable direction are eligible. A raw-only or grade-only export is preserved but does not get an invented numerical conversion. Unknown population/orientation, forecasts, demos, synthetic data, team stints, partial batches and later seasons cannot change opening-state estimates. This guard makes capture metadata consequential: verify it rather than setting “complete” for convenience.

The following are the active metric-to-input mappings; their exact provider names come from the acquisition manifest. They constrain estimates weakly and **do not measure isolated raw technique**. All other metrics are retained for future evidence work or validation, not discarded.

**Deliberately unmapped:** LEBRON/WAR, overall talent totals, role labels/optimization, shot quality alone, minutes, distance traveled, generic turnover rates, general passing composites and action-frequency rates. These do not identify release speed, handle-under-pressure technique, all nine passing-family recognition/execution pairs, conditional tendencies, box-outs, communication, raw strength/speed or conditioning. The manifest flags these distinctions. A generic passing number should not grant 18 separate passing skills. Those channels remain available to richer tagged evidence and scouting rather than fabricated BBI precision.

Calibration is declared, not fitted to game results: a confirmed desirability percentile p supplies `50 + 25*tanh(2*(p−0.5))` as a **weak provisional proxy target**, with a broad ±30 plausibility band within the estimator's existing grade domain. This is not a provider grade-to-game rating claim. It has no pileup at 100. Raw numerical units/letter grades are never silently treated as that scale.

For actual metric-specific samples, weight is `reliability × n/(n+prior_exposure)`, with reliability 0.35 and reference exposures: shots/contests 200, screens/drives/rebound chances 300, possessions 1,000. **These constants are calibration judgments**, not provider guarantees of stabilization. If event counts are absent, minutes use reliability 0.20 with 1,000 prior minutes; if both are absent, a qualitative placeholder uses n=1/prior=4/reliability=0.15, explicitly in qualitative units. Zero known opportunities supplies no evidence. No counts are reconstructed from per75 rates. Historical weights are 1.0, 0.70 and 0.45 for the three eligible seasons; newest eligible season wins. Related BBI evidence shares one provider-overlap ID per player, and only the strongest candidate per input survives, so raw/percentile/grade copies, components and years cannot accumulate as independent votes. Other estimator sources may share underlying basketball events; the low BBI weight does not prove independence from those sources.
